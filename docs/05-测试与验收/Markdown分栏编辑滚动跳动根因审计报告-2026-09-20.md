# Markdown 分栏编辑滚动跳动根因审计报告

> 审计日期：2026-09-20
>
> 审计范围：Markdown Webview 的“分栏编辑”输入、预览渲染、滚动同步和布局边界
>
> 审计基线：`1da57040ab0bf1bb9a0e766761887355a8ed80fc`（修复前 `1.9.98-local.15`）
>
> 修复候选：`1.9.98-local.16`（工作区未提交）
> 审计性质：静态代码审计与历史基线对照；真实 IDE 运行时复现与最终验收仍需补证。

## 1. 一页式风险总览

用户在 Markdown “分栏编辑”状态下输入任意字符时，左侧编辑区及页面发生上下往复跳动；关闭“同步滚动”后仍复现。静态证据表明，输入会在 150ms 防抖后触发完整 Markdown 预览重绘；重绘同时会恢复预览滚动位置、重算编辑/预览行映射，并异步处理图片与 Mermaid。该渲染链路和滚动边界原先未形成明确的“渲染事务”，存在浏览器滚动锚定、布局重排、异步尺寸变化与滚动监听互相影响的条件。

`.16` 已新增 `XLSX Viewer Markdown Scroll Diagnostics` 输出通道，运行时记录 `textarea`、`#preview`、`#content`、Webview document 四类容器在输入/重绘/滚动时的位置、渲染批次和设置状态。发布前定向复核还修正了 document 捕获监听会把子容器滚动误记为 document-scroll 的诊断污染问题：现在仅当事件目标是 document、html 或 body 时才记录 document-scroll。它用于把候选根因转为真实窗口证据；在未取得输出前，仍不能把“固定滚动容器 + 渲染事务隔离”写成已证明的唯一根因修复。

| 优先级 | 问题 | 结论状态 | 建议 |
| --- | --- | --- | --- |
| P1 | 输入后全量重绘与滚动/布局副作用未隔离 | `.16` 已实施候选修复，真实容器待证 | 采集诊断后在三 IDE 验收 |
| P2 | 每次渲染均全量测量行映射 | `.16` 已按同步设置收敛 | 关闭同步时不测量；长文档性能待实测 |
| P2 | 图片、Mermaid 等异步布局未与渲染批次关联 | `.16` 已增加 epoch 守卫 | 含图片/Mermaid 文档验收 |

## 3. 模块与调用链

```text
textarea input
  -> onEditorInput()
  -> debouncedRender(content, 150ms)
  -> renderMarkdown()
       -> Markdown parse / sanitize / preview.innerHTML 全量替换
       -> 恢复 preview.scrollTop / scrollLeft
       -> updateToc()
       -> refreshSyncMetrics()
            -> 全量测量 preview [data-line]
            -> 全量测量 editor 每一行的 offsetTop
       -> requestAnimationFrame()
            -> 搜索重标记 / 目录状态 / 图片 URI / Mermaid 渲染
       -> 图片 load 后再次刷新行映射
```

当前分栏编辑的预期滚动归属应为：左侧 `textarea` 管理编辑滚动，右侧 `#preview` 管理预览滚动，`#content` 只做高度分配，不承担长文档滚动。该预期尚须由运行时数据确认。

## 5. 功能正确性问题

### P1：输入后的全量预览替换没有和滚动副作用组成原子渲染事务

**证据**：

- `src/webviews/md/mdWebview.ts:1198-1212`：每次输入经 150ms 防抖后调用 `renderMarkdown()`。
- `src/webviews/md/mdWebview.ts:890-918`：`renderMarkdown()` 保存 `preview` 位置后，用 `preview.innerHTML = ...` 全量替换预览，再恢复滚动位置，随后继续触发测量和异步后处理。
- `src/webviews/md/mdWebview.ts:1369-1388`：渲染后同步重算编辑区和预览区的行位置。
- `resources/md/mdWebview.css:16-31,207-213,405-478,560-604`：页面、内容区、编辑区和预览区存在多层高度/溢出边界。

**影响**：长文档输入可能触发可见上下跳动、光标上下文丢失、阅读位置感知中断；这是核心编辑路径的可用性问题。

**根因判断**：高置信度确认存在“输入 -> 全量替换 -> 测量/异步布局”链路；中等置信度认为该链路导致截图中的页面跳动。尚无运行时数据证明哪一层容器被移动，因此不能把具体 CSS 属性或同步滚动逻辑认定为唯一直接原因。

**修复方向**：采用方案 D 前先增加仅诊断用途的滚动采样，记录输入前后 `textarea.scrollTop`、`preview.scrollTop`、`#content.scrollTop`、`document.scrollingElement.scrollTop`、渲染批次号、同步滚动状态与 Sticky Toolbar 状态。根据结果将渲染过程限制为一个带版本号的事务：保留用户主动滚动，隔离程序性位置恢复，禁止事务期间的外层滚动锚定和监听器回写。

**验收**：同一长 Markdown 文档连续输入、删除、粘贴、中文输入法上屏时，编辑器及 Webview 外层不发生非用户触发的 `scrollTop` 改变；预览在可允许的内容重排范围内保持相对阅读位置；同步滚动开关两种状态都稳定。

### P2：行映射在每次完整渲染后进行全量 DOM 测量

**证据**：`refreshSyncMetrics()` 在每次 `renderMarkdown()` 后执行；其调用的预览测量遍历 `[data-line]` 并读取 `getBoundingClientRect()`，编辑器测量会为每一行创建隐藏元素并读取 `offsetTop`（`src/webviews/md/mdWebview.ts:1369-1388` 及相邻实现）。

**影响**：文档行数和可映射节点增长时，输入停顿后会产生明显布局计算压力；即便不是直接滚动根因，也会放大卡顿、异步布局交错和可见跳动。

**修复方向**：在方案 D 的渲染事务结束、且布局稳定后再执行一次测量；对未开启同步滚动的场景跳过映射；必要时以 `requestAnimationFrame` 或分帧方式处理大文档。

**验收**：关闭同步滚动时不生成行映射；长文档连续输入时主线程不因逐字符重排而持续阻塞；输入后只保留最新批次的测量任务。

### P2：异步图片和 Mermaid 布局没有渲染批次屏障

**证据**：`renderMarkdown()` 结束后安排本地图片 URI 请求和 Mermaid 渲染；图片 `load` 会再次刷新行映射。当前链路未以渲染版本号明确拒绝旧批次任务。

**影响**：用户快速连续输入时，旧批次的异步回调可能在新内容已渲染后继续触发布局工作，产生额外重排和位置恢复竞争。

**修复方向**：每次渲染递增 `renderEpoch`，异步回调仅在其 epoch 仍等于当前 epoch 时执行；将图片/Mermaid 尺寸稳定后的刷新合并到最新批次。

**验收**：快速连续编辑含 Mermaid/图片的文档时，旧批次不会改写当前批次的测量状态，也不会触发额外滚动恢复。

## 6. 安全审查结果

本次审计以滚动和渲染稳定性为范围，未对整个仓库做完整安全审计。当前问题的建议修复不应降低现有 Markdown HTML 清洗或 CSP 边界：渲染事务只协调滚动、测量和异步时序，不应绕过 `sanitizeRenderedMarkdownHtml()`，不应新增 `unsafe-eval`、宽泛资源域或 Webview 消息权限。

## 7. 性能与稳定性审查结果

- 150ms 防抖并不等于增量渲染；每次稳定输入仍会完整重建预览 DOM。
- 行映射测量与图片/Mermaid 的二次布局叠加，是长文档下风险放大的主要路径。
- Chromium 默认滚动锚定可能参与最终视觉现象，但当前 CSS 未显式禁用或确认其实际作用；只能作为待证假设，不能直接当成根因。

## 8. 架构与可维护性审查结果

当前滚动状态分散在渲染、同步、目录、图片、Mermaid 和 CSS 容器规则中，缺少一个显式的“渲染中/用户滚动/程序恢复”的状态边界。方案 D 应新增最小状态边界，而不是把更多条件散落进多个 `scroll` 监听器。

不建议当前直接采用方案 E（增量 Markdown DOM 渲染）。它会同时改变 Markdown 节点身份、搜索高亮、目录锚点、代码复制、表格、KaTeX、Mermaid、图片解析和选择/滚动恢复逻辑，回归面明显扩大。

## 9. 数据一致性审查结果

该问题主要是 UI 状态与滚动位置一致性，不涉及 Markdown 文件写入、表格数据或持久化状态的完整性。修复时仍须确保：渲染过程中不修改 `currentContent`、不伪造编辑器输入事件、不把程序性滚动误记为用户位置。

## 10. 修复路线与优先级

1. **P0：运行时定位（已实现，待采证）**：`reportScrollDiagnostics` 记录输入、重绘及四层滚动位置；分别验证同步开/关、Sticky Toolbar 开/关、纯文本/含 Mermaid/含图片文档。
2. **P1：方案 D（已实现候选）**：分栏内部滚动、`renderEpoch` 事务、旧异步任务守卫、程序性重绘期间同步隔离、按需刷新映射。
3. **P1：自动化与真实 IDE 验收（进行中）**：schema 测试与静态断言通过；打包、三 IDE 安装和窗口重载后操作验收仍待执行。
4. **长期候选：方案 E（48–96 小时）**：仅当方案 D 后仍不能满足长文档输入性能时，单独立项重构为增量渲染。

## 11. 阻塞项与需要补证的事实

| 待证事实 | 为什么关键 | 证实方法 |
| --- | --- | --- |
| 跳动的实际滚动容器 | 决定修复点是在编辑区、预览区、`#content` 还是 IDE 外层 | 输入前后记录四类 `scrollTop` 与滚动事件顺序 |
| 关闭同步滚动时 Webview 收到的运行时设置 | 源码仅在该设置为真时执行双向同步函数 | 在 Webview 诊断记录中输出当前设置值，且在同一次复现中采样 |
| 问题的版本引入点 | 决定是上游固有问题还是本地布局改动放大 | 同文档/同窗口尺度对比上游、`.12`、`.13+` |
| 图片/Mermaid 是否参与当前复现 | 决定异步布局是主因还是放大器 | 最小纯文本、图片、Mermaid 三组复现 |

## 12. 观察项与反证条件

以下任一事实成立，当前“方案 D 是正式修复方向”的结论需要整体重审：

1. 跟踪显示跳动时根本没有执行 `renderMarkdown()`，或所有 Webview 内部容器位置不变而 IDE 原生编辑器/宿主窗口在滚动。
2. 在禁用预览重绘的诊断条件下，输入仍以相同方式跳动。
3. 同一版本、同一文档、同一设置下，上游基线与本地版本的跳动完全不同，而差异可定位到本次未审计的外部扩展或 IDE 内核行为。

## 13. 可接受风险

采用方案 D 后仍会保留“编辑停顿后全量 Markdown 预览渲染”的成本，特别长文档中不会达到原生增量编辑器的性能上限。这是为控制当前改动范围、保持现有 Markdown 渲染特性而接受的短中期折中；若性能指标不达标，再以独立版本评估方案 E。

## 14. 审计结论

关闭同步滚动仍跳动，已足以否定“只修同步滚动即可”的旧判断。上游 `v1.9.98` 已存在完整预览重绘与同步测量的基础链路；本地 `.13/.14` 的页面高度和工具栏布局改动则可能改变跳动表现的可见程度。两者不是互斥关系：上游链路提供了根本脆弱点，本地布局变化可能成为放大条件。

下一步不应直接盲改 CSS，也不应马上进行高风险的增量渲染重写。先用可删除的运行时诊断确认滚动所有权和事件顺序，再以方案 D 做最小、可回退的事务隔离修复，并以真实 IDE 长文档输入作为最终验收依据。

## 15. 修复后定向复核（发布前）

审计范围：`.16` 新增的滚动诊断、渲染 epoch、图片/Mermaid 异步守卫、同步映射短路和 Split Edit 容器规则。

- **功能与异步**：`renderEpoch` 在每次预览重建时递增；旧帧、图片 load 和 Mermaid 完成回调都会确认仍属于当前批次后才刷新测量。未发现旧批次回写当前预览位置或映射缓存的直接路径。
- **性能**：关闭同步滚动、预览编辑或非编辑状态时，`refreshSyncMetrics()` 清空映射并停止逐行测量；仍保留完整预览重绘成本，这是已明确记录、而非被掩盖的残余风险。
- **安全与隐私**：诊断消息经过共享 schema 校验，字段只包含非负整数位置、短阶段名与两个布尔设置；输出通道不记录 Markdown 正文、文件路径或用户输入内容。未发现新增的文件、网络或持久化写入面。
- **诊断准确性**：初版 document 捕获监听会看到下级元素的 scroll 冒泡捕获路径，可能误把 editor/preview 的事件标为 document-scroll。该 P2 证据污染问题已在本轮修正，并加入静态回归标记；仍需真实窗口验证事件目标在 Antigravity Webview 中的表现。

最终结论：本轮未发现新的 P0/P1 安全或数据完整性问题。`.16` 可以进入 VSIX 安装与真实 IDE 诊断验收；“输入跳动已经彻底消失”仍是待真实窗口补证的结论，不能由本报告或静态测试替代。
